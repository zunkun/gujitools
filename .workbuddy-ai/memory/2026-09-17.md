### 实测暴露的两个 CLI 使用坑

1. **`guji init` 是交互式的，无法脚本化**：它在 `functions/init.py:104` 调

   输入是**文件**时经 `get_extract_output_root` 得到 `<输入父目录>/images`。

## 「去底色左侧缩略图像没加载完」——真因是坐标越界裁白

用户反馈：`去底色图片左侧缩略图没有加载完成，需要等一会再截图吧`。
**用户的观察是对的，但归因（等得不够久）不对。** 这条记录价值很高，
因为真因与表象完全不像，且全程不报错。

### 排查过程（含一次中途的错误结论）

1. 先按用户猜测做了「等更久」：新增 `wait_for_thumbnails()` +
   `_visible_strips()`，用 `icon.pixmap(96,128).cacheKey()` 与
   `strip._placeholder` 比对，轮询到占位归零。**跑起来 0 超时** → 图标其实早就换好了。
2. 一度以为是 Qt 的 `QListWidget` IconMode 离屏不绘制。做了大量对照实验：
   - 独立 `ThumbStrip`（800px 高、12 条）→ **每条都画得很好**（1.2 万+ 非白像素）；
   - 真实实例里各种 `viewport().update()/repaint()`、`doItemsLayout()`、
     `setIconSize/setGridSize` 重设、逐条 `scrollToItem` → **全都没变化**；
   - 中间还踩了一个假象：把像素采样窗口取成 x∈[12,140]（窗口级 grab 的
     strip 左边缘），量到的是滚动条/边框而不是图标区，得出过「图标没画」的错误结论。
3. **决定性一步**：把真实 app 的 12 个 `item.icon()` 拆出来单独量亮度 →
   ```
   icon0: 96x128 非白=0   (0%)   ← 全白
   icon1: 96x128 非白=676 (5%)   ← 有内容
   icon2: 96x128 非白=0   (0%)   ← 全白
   ```
   **隔一条全白一条正常** —— 说明问题在图标内容本身，不在绘制。

### 真因

`_page_thumb_for()` 用 `sx = 缩略图宽 / image_size 宽` 把**检测框坐标**
（阶段图坐标系）换算到缩略图上。而 `_copy_real_demo()` 里
`save_image_size()` 写的是 **缩放后缩略图的尺寸**（700×690），
但 extract 目录里实际存的是 **2400×2367 的原图**，检测框也是 2400 尺度的。

于是 `sx = 700/700 = 1.0`，2400 尺度的框被直接拿去裁 700px 缩略图：

| 条目 | 框 | 结果 |
|---|---|---|
| `-l` | `[30,513,1103,2064]`，x 部分重叠 | 裁出 **1%** 深色的白条 |
| `-r` | `[1271,523,2367,2069]`，x 起点 1271 > 700 | 完全越界 → **0% 纯白** |

**修复**：`save_image_size()` 改传 `original.width()/height()`（阶段图尺寸）。

修完 `scaled_box` 变成 `[8.8,149.5,321.7,601.7]` / `[370.7,…,690.4]`，
正确落在 700px 缩略图内，深色占比从 0~1% → **29~35%**，左侧缩略图全部显出真版面。
