## cli / desktop 双入口模块化解耦重构

**背景**：cli 与 desktop 做同一件事（extract/detect/rembg/cropremove/print），
但各自维护参数构造、默认值、输出目录规则、状态语义，存在四处重复。

**完成的重构**：

1. 新建 `core/` 中立共享层（不依赖 cli/desktop/functions）：

   - `core/result.py`：`StageStatus` 枚举 + 退出码/状态字符串双向转换。
   - `core/__init__.py`：统一导出。

   `from cli.command_args import CommandArgs`，改为依赖 `core.args.ArgsProvider` 协议。
   验证：阻断 cli 包导入后 `functions` 仍可正常导入与构造。

4. **统一状态语义**：`desktop/pages/taskdetail/runner.py` 的 `STATUS_LABELS`

5. **cli.py 职责收窄**：抽出 `cli/config_io.py`（YAML 读取 + `ConfigError`），
   `main()` 返回退出码而非深层 `sys.exit`；删除 init 分支与 execute_command

6. **修掉私有方法穿越**：`desktop/stages/generic_stage.py` 原调
   `interceptor._consume()`，`events.py` 新增公开 `drain_pending()`。

7. 兼容 shim：`cli/command_args.py`、`cli/init_args.py` 改为转发 `core.args`。
8. `guji.spec` 增加 `collect_submodules('core')`。

## 第二轮：修复隐藏 bug + 删除重复/多余代码

用 `python -m pyflakes` 全量静态扫描 + 逐处人工复核，共发现并修复 6 个真实缺陷。

### 修复的隐藏 bug

1. **`functions/print.py` 不指定 pdf_name 必崩**（最严重）。
   `get("pdf_name", "output.pdf")` 的兜底永不生效——`CommandArgs` 总会注入
   `pdf_name` 键（默认值 `None`），键存在时 dict.get 的默认值不触发，
   于是 `out_dir / None` 抛 `TypeError`。CLI 上 `guji run print` 不带
   `pdf_name` 必然崩溃。改为 `get("pdf_name") or "output.pdf"`。
   **通用教训**：凡默认值为 None 的参数，`get(key, fallback)` 兜底均失效。
   受影响键清单：extract(pages/start/end)、crop/rembg/cropremove(border)、
   print(pdf_name/left_page_margins/right_page_margins/title_switch_nodes/
   page_number_end_page/skip_pages/files)。其余各处已用 `or` 或显式判空处理。

2. **`functions/base.py` 的 clean 默认值与全局规格冲突**。
   `get("clean", True)` 与 `core.command_spec` 的 `False` 相反——任何不经
   `CommandArgs` 的调用会静默 `rmtree` 用户输出目录。已统一为 `False`。

3. **`utils/pdf_utils.parse_color` 三个问题**：非法值静默返回黑色（用户打错
   "0,0" 只得到黑字 PDF 无提示）、超范围分量直通（`300,0,0` → 损坏 PDF）、
   失败方式不一致（`abc` 抛错但 `0,0` 静默变黑）。已统一为：
   **非法一律抛 ValueError**，校验分量 ∈ [0,255]。

4. **颜色参数无校验**：CLI 的 `run print` 路径此前不校验颜色格式。已在
   `core.command_spec._validate_print` 中接入 `validate_color_fields`。

5. **GUI 侧从不调用 `validate()`**：桌面端只靠各面板 `get_args()` 自查，
   导致「命令行拒绝、界面放过」的行为分叉。已在
   `desktop/stages/generic_stage.run_stage` 中补上 `command_args.validate()`。

6. **`desktop/store/json_io.write_json` 文档与行为不符**：docstring 称
   父目录缺失时「放弃写入并返回 False」，实际却 `raise FileNotFoundError`
   （两个调用方都靠额外 mkdir 兜着）。已改为真正返回 bool。

7. **死代码**：`utils/pdf_utils.py` 有一处重复计算且从未使用的 `batches`；
   一处 `from unittest.mock import DEFAULT`（误自动导入的遗留）；
   `desktop/components/log_panel.py` 的 `QTextEdit` 未定义（靠
   `from __future__ import annotations` 侥幸不崩，已改 TYPE_CHECKING 导入）。

### 删除的重复实现（合并到 utils 最低层）

## 第四轮：修复第四步 print 列表「文字与图片距离过大」

**用户反馈**：`area=2` + `border=None` 时，第四步 print 图片列表里图片文字和
图片距离比较大（图片高度比较大）。

### 定位结论：不是几何 bug，是列表项布局 bug

先排除了 area/border 几何嫌疑——`utils.box_geometry` 输出的画布尺寸是对的：

| area | border | 画布 | ratio | full_page |
|---|---|---|---|---|
| 2 双框 | None | 2481x3508 | 1.414 | True |
| 2 双框 | 10mm | 1920x2620 | 1.365 | False |
| 1 双框 | None | 900x2600 | 2.889 | False |

**真正根因** 在 `desktop/components/viewers/print_preview.py`：

```python
ICON_SIZE = QSize(180, 240)   # 图标框
GRID_SIZE = QSize(200, 290)   # 条目固定网格
item.setTextAlignment(Qt.AlignHCenter | Qt.AlignBottom)
```

条目被强制成 200x290 固定框，图标只占顶部 240px，而文字被 `AlignBottom`
**钉在网格最底部** → 图片下沿到文字之间**恒定空出 50px 死区**，与图片
宽高比无关。该空档在三种情形下都存在于代码里，只是观感不同：

- `area=2 + border=None` 输出**整页画布**（ratio 1.414），缩进 180x240
  图标框几乎占满 → 「图片 → 50px 空白 → 文字」对比最强烈（用户看到的就是这个）；
- `area=1` 输出 900x2600（ratio 2.889），只占图标框中间约 83px 宽，同样的
  50px 显得不刺眼。

**Qt 实测确认**：`visualItemRect` 返回 `200x290`，与图片比例完全无关。

### 修复

`print_preview.py`：
- 新增 `LABEL_H = 44`（文件名区高度）；
- `GRID_SIZE = QSize(200, ICON_SIZE.height() + LABEL_H)` → 200x284，
  图标与文字**紧邻**，不再有中间死区；
- 文字对齐由 `AlignBottom` 改为 `AlignVCenter`（避免被推出紧邻区）。

顺带清理该文件三个死导入（`shutil` / `QFileDialog` / `ToolButton`——
下载/插入逻辑早已移到 `desktop/pages/taskdetail/print_list.py`）。

附带修掉 `desktop/components/log_panel.py` 的 `QTextEdit` 未定义名
（靠 `from __future__ import annotations` 侥幸不崩），改为 `TYPE_CHECKING` 导入。

### 验证

- 新增 `tests/selftests/print_list_layout.py`（10 断言）把该不变量钉住：
  网格高 = 图标高 + 文件名区、死区为 0、文字不得用 AlignBottom、
  并复现 `area=2 + border=None → 整页画布` 的回归语境。
- GUI 全量自测 **257/257 通过**（247 + 10）。
- pyflakes 对改动文件干净；分层依赖复检仍零反向依赖。

## 第五轮：把 detect 提升为 functions 层的真实命令（用户设计对齐）

**用户的设计意图**（原话）：
> detect 就是「检测图中 2 个文本框」；crop 被处理时它应当去检测 2 个框。
> CLI 与 desktop 处理图片是一样的（同样的排序/extract/rembg/crop/print 算法），
> 只是参数不同。

### 发现的真实缺口

改造前 `functions/` 下**没有** detect 模块。`COMMAND_SPECS` 里那条
`detect` 是**占位**（`defaults={}`，无对应模块）。检测被三处各自实现：

| 位置 | 形式 |
|---|---|
| `functions/text_region.py` | 直接 `utils.detect_left_right_boxes` + `[0][:4]` |
| `desktop/stages/detect_stage.py` `run_detect` | 同样调用 + `[0][:4]`（写了一遍） |
| `desktop/stages/detect_stage.py` `run_detect_stage` | 又写一遍同样的调用 + `[0][:4]` |

三处同算法、零共享；`page_boxes` 事件也在两处各写。且 **`guji detect` 不存在**，
所以「检测」这一步无法单独在 CLI 上运行（GUI 有第二步、CLI 没有对应物）。

### 改动

1. **新建 `functions/detect.py`**（检测的唯一所有者）：
   - `extract_first_box(boxes)`：从 `[(x1,y1,x2,y2,area),...]` 取 `[0]` 的前 4 个
     并转 int —— 原先 CLI/GUI 各写一遍的 `[0][:4] if ... else None` 收敛到此处；
   - `detect_page_boxes(img_bgr, model=None)`：**检测算法的唯一入口**，
     model 为 None 时用进程内单例；
   - `DetectFunction`：**重写 `execute()`**（基类语义是「建输出目录→处理→落盘→
     统计写出数」，检测只上报坐标、不该凭空建目录）。保留了基类相同的
     并发（`min(8, 页数)`）与 2 轮重试、以及 `progress_total` + 逐页 `progress` 上报。
2. **`TextRegionProcessor` 改为 `from functions.detect import detect_page_boxes`**，
   crop/cropremove 不再自调 `utils` 原语。

## 第 9 轮 · detect 输出目录语义修正（sibling，非嵌套）

**用户报的真实 bug**：
```
python main.py detect -i C:/Users/liuzu/Documents/test/a/images --save
输出目录：C:/Users/liuzu/Documents/test/a/images/detect   # ← 错：嵌进输入目录里
```

**根因**：`functions/detect.py::_resolve_outpath` 在「目录输入 + 无 -o」

- 不带 `--save` → `self.outpath = None`，**不计算路径、不建目录、不写文件**，

## 第 10 轮 · detect 命令行空跑拦截（CLI 层）

**用户要求**：detect 作为代码调用（中间步骤）可用；命令行有 `--save` 时生成
标注图；**命令行不带 `--save` 属于空跑浪费资源，应提示并拒绝**。

**设计取舍（关键）**：拦截只放在 **CLI 入口**，不进 `CommandArgs.validate()`。

| 调用方式 | 不带 `--save` | 为什么 |
|---|---|---|
| 命令行 `guji detect` | ❌ 拒绝 | 坐标只打到 stdout，无产出去处 |
| `guji run detect`（配置 save:false） | ❌ 拒绝 | 同上 |
| 代码 `DetectFunction(...)` | ✅ 可用 | 中间步骤，坐标由调用方消费 |
| 代码 `detect_page_boxes(img)` | ✅ 可用 | 纯函数，crop/cropremove 在用 |
| GUI detect 阶段 | ✅ 可用 | 坐标经事件通道交给界面画框 |

**⚠️ 为什么不能放 validate()**：`CommandArgs.validate()` 是 CLI 与 GUI
**共用**的。若在校验层强制 `save`，GUI 的 detect 阶段（本来就不落盘）会被
一并拦死。已验证 `_validate_detect` 函数体（剥掉 docstring）不读取 `save`。

**实现**：
- `cli/cli.py::_reject_dry_run(command, command_args)`：仅对 `detect` 生效，
  `save` 为真则放行；否则打印 `_DRY_RUN_HINT`（含正确用法 + crop/cropremove
  替代路径 + 代码调用说明）并返回 True。在 `main()` 的 `validate()` 之后、
  `execute_command()` 之前调用，返回 FAILED 退出码（1）。
- `core/command_spec.py`：新增 `_validate_detect`（只校验 ext），
  `COMMAND_SPECS["detect"].validators` 登记它。
- 拒绝路径**无磁盘副作用**（有断言守卫）。

**⚠️ 顺带修掉模板不一致**：`static/guji.yaml` 的 detect 段原本 `save: false`，
而 `guji run detect` 现在会拒绝 → **模板自己跑不起来**。已改为 `save: true`
