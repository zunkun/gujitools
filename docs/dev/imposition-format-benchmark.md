# 拼版成品格式对比报告：PNG vs JPEG

> 日期：2026-10-24
> 范围：`stages/imposition` 拼版成品页的编码格式（PNG / JPEG），以及它对下一步
> 「PDF排版」生成耗时与成品 PDF 体积的影响。
> 本报告**只做测量，未改任何代码**。

## 结论摘要

1. **PNG 明显更小**：同一批拼版页，PNG 平均 1.0MB/页，JPEG q95 4.8MB/页
   （**4.6 倍**）；即使 JPEG q85 也有 3.2 倍。拼版页是大面积白/透明的稀疏文字，
   正是 PNG 的最优场景、JPEG 的最差场景。
2. **JPEG 只在编码速度上占优**：拼版落盘时 JPEG 约 50ms/页，PNG 约 400~500ms/页
   （快 8 倍）。但这 8 倍只省下每页零点几秒的写盘时间，代价是成品体积翻数倍。
3. **下一步「PDF排版」里，JPEG 的收益取决于是否直嵌**：
   - 走**当前代码**（解码 → 灰度 L → Flate 重压）：JPG 反而**更慢、更大**
     （8.84s / 86.2MB vs PNG 8.17s / 76.3MB）。
   - 走**JPEG 直嵌**（DCTDecode，不解码不重压）：排版只要 **1.2s**（快 8 倍），
     但 PDF **239MB**（3.1 倍）。
4. **建议保持 PNG**。当前「后缀随源图」的策略（源图全 jpg 才出 jpg）是合理的；
   若嫌拼版写盘慢，可把 PNG 压缩级别从 6 降到 3（省 16% 时间、体积 +17%），
   但**不建议换 JPEG 格式**。真正值得继续提速的是 PNG→Flate 那条链路
   （逐页 zlib 串行），而不是换有损格式。

## 1. 测试环境与素材

| 项 | 值 |
| --- | --- |
| 机器 | Windows，Python 3.10，Pillow 12.x |
| 排版口径 | A4 横向、300DPI（图片最长边 ≤ 2940×2007）、边距 20mm |
| 主素材 | 任务 0017：50 页拼版成品，4363×3209 RGBA，共 51.4MB |
| 抽样对照 | 任务 0002（1426×934，稀疏页）、0004（3065×2429，密集页）各取前 8 页 |
| JPEG 参数 | Pillow `quality=95/90/85`，白底压平后 RGB 编码（与生产 `JPEG_QUALITY=95` 同一口径） |

> 拼版成品当前规则（`desktop/services/imposition.py`）：**后缀随源图**——
> 一页的源图全是 jpg/jpeg 才出 `.jpg`，否则出 `.png`（保住透明底）。
> 任务 0017 的源图是去底色 PNG，所以成品全是 `.png`。

## 2. 拼版成品的体积与编码耗时

### 2.1 任务 0017（50 页，4363×3209）

| 变体 | 总大小 | 平均/页 | 相对 PNG | 编码耗时/页 |
| --- | ---: | ---: | ---: | ---: |
| **PNG RGBA（现状）** | **51.4MB** | **1029KB** | 1.00× | 494ms |
| PNG RGB（白底，模拟 JPEG 前置） | 57.6MB | 1153KB | 1.12× | 503ms |
| PNG RGB + compress_level=9 + optimize（白底） | 55.1MB | 1101KB | 1.07× | 1088ms |
| JPEG q95 | 239.0MB | 4781KB | **4.65×** | 253ms（含白底压平） |
| JPEG q90 | 188.6MB | 3771KB | 3.67× | 248ms（含白底压平） |
| JPEG q85 | 162.1MB | 3241KB | 3.15× | 244ms（含白底压平） |
| JPEG q95 灰度（转 L） | 235.6MB | 4713KB | 4.58× | 263ms（含白底压平） |

要点：

- **透明底是 PNG 的体积优势来源**：白底 PNG 反而比 RGBA PNG 大 12%
  （51.4 → 57.6MB），因为整片透明区几乎不占字节。
- JPEG 的「253ms/页」里约 200ms 是白底压平（alpha 合成），JPEG 编码本身
  约 50ms/页；PNG 编码本身约 400~500ms/页。
- 灰度 JPEG 并不比 RGB JPEG 小多少（-1.4%）：纯灰内容在 JPEG 里色度通道
  本来就被压得很便宜，而亮度通道才是大头。

### 2.2 跨任务抽样（各前 8 页，平均/页）

| 任务 | 页面尺寸 | PNG | JPEG q95 | JPEG q90 | JPEG q85 |
| --- | --- | ---: | ---: | ---: | ---: |
| 0002（稀疏） | 1426×934 | **225KB** | 839KB (3.7×) | 655KB (2.9×) | 563KB (2.5×) |
| 0004（密集） | 3065×2429 | **2134KB** | 2640KB (1.24×) | 2062KB (**0.97×**) | 1761KB (0.83×) |
| 0017（中密） | 4363×3209 | **1297KB** | 4863KB (3.7×) | 3826KB (2.9×) | 3279KB (2.5×) |

结论：**只有「内容极密的扫描页」JPEG q90 才与 PNG 持平**（0004：2062KB vs
2134KB），而 q95 仍然更大；其余场景 PNG 小 2.5~3.7 倍。任何情况下 JPEG 都不会
明显小于 PNG。

## 3. PNG 自身的压缩参数

任务 0017 前 6 页，RGBA PNG 不同压缩级别（Pillow `compress_level`）：

| 级别 | 编码耗时/页 | 平均体积 | 相对 level 6 |
| --- | ---: | ---: | --- |
| 0 | 496ms | 56.0MB（未压缩） | 46.8× |
| 1 | 360ms | 2451KB | 2.05× |
| 3 | 381ms | 1399KB | 1.17× |
| **6（Pillow 默认，生产现状）** | **451ms** | **1195KB** | **1.00×** |
| 9 | 1707ms | 1117KB | 0.94× |

- 默认 6 已是合理折中；**级别 9 时间 3.8 倍、只省 6.5%**。
- 若拼版阶段嫌慢，可考虑级别 3：时间 -16%、体积 +17%（格式仍是无损 PNG）。

## 4. 下一步「PDF排版」的实测

### 4.1 任务 0017，50 页，同一套排版参数

| 输入端 | PDF 排版耗时 | 成品 PDF | 说明 |
| --- | ---: | ---: | --- |
| **PNG-RGBA（现状）** | 10.03s | **76.3MB** | 解码 → 压平 → 灰度 L → Flate |
| PNG-RGB（白底） | **8.17s** | 76.3MB | 省掉逐页 alpha 合成（-1.9s） |
| JPG q95（走当前代码） | 8.84s | 86.2MB | JPEG 解码快，但又转 L + Flate 重压 |
| **JPG q95（直嵌 DCTDecode）** | **1.24s** | 239.1MB | 不解码、不重压，原字节进 PDF |
| JPG q90（直嵌） | 1.04s | 188.6MB | 同上，体积小一些 |

关键点：

- 走**现有排版代码**时，JPEG 的画质噪声会**降低 Flate 压缩率**：PDF 从 76.3MB
  涨到 86.2MB，速度也没提升（8.84s vs 8.17s）——两头都亏。
- 只有让排版**直接嵌入 JPEG 原始字节**，速度才降到 1.2s；但成品 PDF 变成
  239MB，是 PNG 方案的 **3.1 倍**。

### 4.2 跨任务抽样（各 8 页）

| 任务 | PNG → PDF | JPEG q95 直嵌 → PDF |
| --- | --- | --- |
| 0017 | 2.27s / 12.45MB | 0.42s / 38.91MB（3.1×） |
| 0004（密集） | 1.64s / 11.20MB | 0.36s / 21.12MB（1.9×） |
| 0002（稀疏） | 0.54s / 1.55MB | 0.32s / 6.72MB（4.3×） |

密集页的 PDF 体积差距最小（1.9×），但也没有反超 PNG。

## 5. 画质

与「白底 PNG 无损图」逐像素比对（前 6 页）：

| 编码 | PSNR | 最大误差倾向 |
| --- | ---: | --- |
| JPEG q95 | 49.2~50.6 dB | 文字边缘有轻微振铃，肉眼基本不可见 |
| JPEG q90 | 43.5~44.5 dB | 放大可见边缘毛刺 |
| JPEG q85 | 40.1~40.7 dB | 边缘毛刺明显，细笔画可能发虚 |
| JPEG q95（灰度） | 与 q95 相同 | 同 q95 |

PSNR 数值不低，但**古籍细笔画对 JPEG 的 8×8 块效应比照片敏感**——放大查看
时 q90 以下在笔画末梢可见毛刺。PNG 无损，不存在这个问题。

另外 JPEG 方案的隐性代价：拼版成品必须**白底压平**，透明底被固化，之后编辑、
预览、导出都拿不回透明信息（当前 PNG 成品保住了透明底）。

## 6. 结论与建议

| 问题 | 结论 |
| --- | --- |
| PNG 与 JPG 体积差多少？ | 稀疏/中等密度页 JPG 是 PNG 的 **2.5~4.6 倍**；极密页 q90 才与 PNG 持平 |
| PNG 压缩还能再省吗？ | 级别 6→9 时间 3.8 倍只省 6.5%；6→3 省 16% 时间、体积 +17%。默认 6 合理 |
| 后面还有 PDF 排版，JPG 更好吗？ | **否**。现有链路下 JPG 更慢更大；除非改成直嵌，而直嵌会让 PDF 大 2~4 倍 |
| 建议 | **保持 PNG**，保留「后缀随源图」策略；继续提速应针对 PNG→Flate（逐页 zlib）链路 |

可选方案（按优先级）：

1. **维持现状（推荐）**：拼版出 PNG，PDF 排版走已优化的「灰度 L + zlib 3」。
2. **拼版写盘想更快**：PNG `compress_level` 6 → 3（无损、-16% 时间、+17% 体积）。
3. **只在「生成速度 > 文件体积」的产品取舍下**才考虑 JPEG：还需要同时改
   PDF 排版为 JPEG 直嵌，否则 JPEG 在现有链路里是负收益。
4. 若下一步继续优化 PDF 排版，方向应是**把逐页 Flate 压缩并行化**，
   而不是换图像格式——它以无损、体积不变的方式拿回大部分串行时间。
