## 操控变形（puppet warp）"拖动卡死、不能实时"的根因与修复

用户原话："程序卡死崩溃，并且不能实时查看" + "gimp 方案虽然不满意，但是能实时
查看，不卡顿" + "我看这个操作，只影响节点附近的像素，不影响全局"。

### 实测结论（推翻/修正了此前几条估计）

1. **ARAP 不是局部的**（量化钉死）：拖**一个**图钉 100px，`mesh_region`
   仍是整图的 **96~98%**。即使用"两钉钉死两侧、拖中间"的 PS 典型用法，
   区域照样 96%。原因：ARAP 位移场缓慢衰减但**永不归零**。
   ⇒ **裁剪 `mesh_region` 没有收益（只省 ~4%），不要做。**
   （此前跟用户说的"95% 顶点会动"，现在在像素级再次确认。）

2. **逐像素重映射的 numpy 下界 ≈ 0.7 µs/像素**（内存带宽受限）。
   拆开实测（1200×900 = 1.08M 像素）：
   - 纯双线性采样 1.08M×3ch：**336ms**
   - 纯重心坐标 1.08M：**101ms**
   - 一次 gather 1.08M×3ch：**38ms**
   - 固定开销（两张 NaN 表 + `src.copy()`）：仅 **7ms**，可忽略
   ⇒ 已经贴到 numpy 下界，**微优化空间为零**。任何"再快一点"的尝试
   （float32 顶点坐标、融合光栅化+采样、扫描线、格张量）都只拿到
   -15%~+5%，且引入正确性回归。**别再走这条路。**

3. **真正的杠杆是"降分辨率预览"**（成本随像素数近线性）：
   | 预览像素 | 耗时 |
   |---|---|
   | 8 万 | 43ms |
   | 12 万 | 72ms |
   | 20 万 | 140ms |
   形变场是低频的、预览图再由 Qt `SmoothTransformation` 放大，肉眼看不出差别。

4. **求解耗时随顶点数超线性**，且"只按倍数粗化"不够：
   最密档 20px 在 4000×3000 下有 3 万顶点，×4 后仍剩 1989 顶点 ≈ 单次 **103ms**。

- `utils/puppet_warp.py`

  - `utils/__init__.py` 的 `_LAZY` 登记 `drag_cell`。

## 二、重影修复：形变预览「原图还压在背景上」（用户报障续）

**报障**：「编辑图片的时候，比如拖动图片变化形态，图片变换了，但是原图片还是
在背景上面」→ 追问确认症状 =「形变结果和原图重影/叠着」。

**根因**：形变预览是**局部浮层**（QGraphicsPixmapItem，Z=4），底图
（self._item，Z=0）仍是一整张**未擦除的原图**。形变结果让开的位置，底图里的
**旧像素就透出来**——看上去两张图叠着。变换工具早就有这个处理（把选区填白再画
浮层 _float_item），形变工具当时没有。

**修法**：引入「挖空」机制——
- 新状态 self._preview_cutout: QRect | None（底图上被挖空的框，图片坐标）
  + self._alpha_known: bool | None（源图是否真含透明像素的缓存）。
- 新方法 _paint_canvas_cutout(rect)：把底图重画成「原图 + 指定矩形挖空」——
  CompositionMode_Source 填白（不透明源图）或填透明（有透明像素的源图）。
  rect=None = 回填（重铺原图）。
- 新方法 _has_alpha()：**实扫 alpha**（不能用 hasAlphaChannel() 单判：
  ARGB32 有通道 != 真有透明像素；全不透明还填透明会在 Windows 显成黑）。
  结果按图缓存（_alpha_known），换图/就地改像素时失效；每帧扫会白吃几十 ms。
- 接线：_refresh_cage_preview / _refresh_deform_preview 画完浮层后调
  _paint_canvas_cutout(受影响框)；_clear_cage_preview / _clear_deform_preview
  清浮层时回填；refresh()（就地改像素后重刷底图）**要把上次挖空重挖一遍**，
  否则重刷会把挖空抹掉、重影复活；set_image 重置新状态。
- 挖的是**受影响框**（warp_region/mesh_region），不是整幅——形变是局部的，
  框外逐字节等于原图，不动。

**验证**：
- 新增 11 条重影回归断言（image_editor.py）：笼/变形各钉「预览时挖了框 /
  框内是纯白 / 框外仍是原图 / 清预览后回填」+ 透明源图「判定有透明像素 /

- 离屏渲染合成场景截图肉眼确认：预览态黑块跟着笼形变、**底下无残影**；
  清预览态原块完美还原。
- 全量（跳过既有环境失败模块）：**1592 项全绿**。gen_api_docs + check_docs 通过。

## 续：两条新约束（用户 2026-10-02）

用户原话：
1. 图片编辑区域不要铺满整个界面，上下都预留空白地方，方便后续操作
2. 图片操作现在受原始图片边界限制，假如图片倾斜后一部分区域超出原本边界，
   现在会被截图（截掉），这个不对。**不要截图**，最终结果要按**最后**图片的
   范围，而不是最初的图片范围

用户后续两句话把约束 2 的口径彻底钉死（**推翻了"保留框外原图内容"的中间方案**）：
- 「原图丢弃，只显示新图，无论边界在哪里，新图都完整显示」
- 「一切以新图为准，新图什么样就什么样，老图不要了」

### 约束 1：编辑区留白
- 新常量 `EDIT_FIT_RATIO = 0.8`（`desktop/components/viewers/image_editor.py`）。
- `_fit_ratio` 缺省从 1.0 改成 `EDIT_FIT_RATIO`；`_set_tool` **每个工具都**调
  `set_fit_ratio`：变形/变换笼用 `DEFORM_FIT_RATIO`（也是 0.8），其余用
  `EDIT_FIT_RATIO`。**所有工具都不再铺满视口**。

### 约束 2：内容外框（grow）
四个工具都支持，返回 `(结果, (ox, oy))`（ox/oy 可为负 = 新画布左上角在原坐标系位置）：
- **校正**：本来就用摆正后的四边形**替换**整幅图（老图已丢弃）⇒ 无需改。
- **变换**：`bake_transform(..., grow=True)` + 新函数 `transform_region()`。
- **变换笼**：`deform/deform_qimage(..., grow=True)` + `content_region()`。
- **变形**：`puppet_warp/puppet_warp_qimage(..., grow=True)` + `_grow_box()`。

**统一口径（关键，反复踩）：最终画布 = 操作后内容的紧外框，不是"原图 ∪ 内容"。**
- 变换：内容 = 变换后的选区 ∪ 选区**之外**原图残余条；选区原位被移走、
  被填白 ⇒ **不算进外框**（否则整体平移会凭空多一条白边）。
- 变换笼/变形：RBF/网格是局部的，**没碰到的像素逐字节不变、仍占 [0,W]×[0,H]**
  ⇒ 它**就是**结果的一部分，必须留全 ⇒ 外框 = 原图边界 ∪ 被拖把手/顶点落点。
  ⚠️ 这里**不能**再叠加影响半径 R：R 是 RBF 位移场尺度（实测拖 25px 算出
  R≈64），叠加后向内拖也会凭空外扩 64px。已从 `content_region` 去掉。
  `_grow_box` 本来就没叠 R，正确。

### 踩到的坑（值得记）
1. **1px 画布膨胀**：鼠标→像素映射带小数（实测平移 −30.048465），
   `floor(−30.048) = −31`、`ceil(169.952) = 170` ⇒ 多 1 列。变换后坐标改
   **`round`**；但"原图残余条"是未变换的整数矩形，仍用 `floor/ceil`（向外守边界）。
2. **`refresh()` 的"重挖"注释已过时**：现在挖的是**整张原图**
   `QRect(0,0,W,H)`（grow 后浮层被移到任意 origin，只挖小框会让没盖到处透出旧
   像素 = 重影本身）。`_paint_canvas_cutout` docstring 已改。
3. **`resizeEvent` 会覆盖显式 `fit(ratio)`**：`_user_zoomed=False` 时每次
   resize 都按 `_fit_ratio` 重新 fit。测试里要让"铺满"基准准确，得**临时**
   `set_fit_ratio(1.0)` 量完再还原，不能只调 `fit(1.0)`。
4. **`transform_shear` 语义**：绕 `rect.top()` 做 y 随 x 斜切 `y' = y + k·x`；
   不是"绕边中点"。断言要按这个写（k=0.5、右缘中点 ⇒ 下移 0.5·w）。
5. **测试环境残留**：改了 selftests/*.py 后 `__pycache__/*.pyc` 会短暂读到旧

## 导航默认折叠 + 共用步骤组件层（`desktop/steps`）+ 三个模块改用它

用户原话（三条）：
> 1. 左侧的目录，默认关闭
> 2. 图片提取，图片去底色，拼图 目录 功能启用任务管理的 图片提取
> 3. 任务管理的相关步骤代码解耦，因此 左侧目录中的 图片提取，去底色，拼图
>    可以调用共用组件，并且这3个menu 功能相互不影响

AskUserQuestion 两条答复钉死了口径：
- **架构**：复用组件，但**必须抽出公共组件**；任务管理各步骤**有先后关系**，
  所以模块组件**不需要相互关联**，公共组件**定义好 API 就行**（入口文件/目录、
  输出文件/目录）；「新的功能可以批量处理也可以处理一张图片」。
- **粒度**：**执行内核 + 面板**（不是连界面外壳一起抽，风险可控）。

### 1) 导航默认折叠（`desktop/modules/shell.py`）

- **删掉 `ModuleShell.resizeEvent` 里那句 `nav.expand(useAni=False)`** —— 它才是
  "启动即展开"的真凶（壳层在 `show()` 之前构造，所以当初只能自己补一次）。
- qfluentwidgets 的 `NavigationPanel` 默认 `displayMode = COMPACT`；且它**只在
  "菜单按钮不可见"时**才在 resize 里自动展开，本程序一直显示菜单按钮 ⇒
  不主动 expand 就**稳定保持折叠**。
- 新增 `nav_is_expanded()` / `toggle_nav()`（自测与将来的快捷键入口）。
  ⚠️ **`NavigationInterface` 只有 `expand()`，没有 `collapse()`**（收回在
  `panel` 上）——自己拼 expand/collapse 会踩 `AttributeError`，必须走
  `NavigationInterface.toggle()`。
- 自测里 toggle 回来要注意：**展开动画没跑完时 `panel.collapse()` 会直接
  return**（防动画打架），所以先 `pump` 够时间再切。

### 2) 新增共用步骤组件层 `desktop/steps/`

| 文件 | 职责 |
|---|---|
| `spec.py` | `StepSpec`（command/面板/输入种类/默认输出/过滤串）+ `SPECS` + `spec_by_key`。**Qt-free**，可被纯逻辑导入 |
| `kernel.py` | `StepRequest`(源/输出/参数) + `StepKernel`(QThread 执行内核) + `CommandJob` / `CallableJob` |
| `control.py` | `StepControl`：源选择 + 面板 + 输出目录 + 执行/中断 + 状态行，发信号不弹窗 |
| `process.py` | `StageProcess`：**子进程**传输层（起进程/字节流/看门狗），任务管理用 |
| `__init__.py` | PEP 562 惰性导出（`control`/`process` 会拖进 PySide6，分开导入） |

关键决定（都写进了 docstring，改之前先读）：

1. **`CommandJob` 显式把 `function.outpath` 设成 `request.dest`** —— 不设的话
   rembg 会在用户给的目录后**再追加一层 `rembg/`**（`resolve_final_output_dir`
   的规则），而模块页按 `dest/<stem>.png` 找结果 ⇒ **永远找不到**。这是上一轮
   模块页就埋着的 bug，这次顺手修了（实测产物落在 `1_去底/1.png`，不再是
   `1_去底/rembg/1.png`）。
2. `StepSpec.panel` 支持两种写法：`"ExtractPanel"`（默认在
   `desktop.components.panels` 找）与
   `"desktop.components.imposition:ImpositionPanel"`（**拼版面板不在那个包里**）。
3. 内核的信号**必须连到主线程对象的绑定方法**再转发（`worker.progress.connect
   (self._on_progress)`），不能 `signal.connect(signal)`——否则槽可能跑在子线程
   （同 `desktop.workers` 的规矩）。
4. **三个模块各持自己的一份 `StepControl`**（各自的内核/源/输出）⇒ 互不影响，
   没有共享可变状态。

### 3) 三个模块页改用它（`desktop/modules/{extract,rembg,imposition}/page.py`）

- 各自删掉自己写的 `_ExtractWorker` / `_RembgWorker` / `_ComposeWorker`；

### 4) 任务管理步骤代码解耦（`desktop/pages/taskdetail/runner.py`）

## 第五批（同日续）：修两个真 bug + 把「提取 → 去底色」这条链接通

### 1) 导航点不动（真 bug，用户肉眼可见）

- **根因**：`qfluentwidgets` 的 `NavigationWidget.clicked` 是 **`Signal(bool)`**，
  壳层把 `onClick` 直接连成 `lambda: self.show_module(key)` 时，槽的第一个位置
  参数会收到 `True` → `show_module(True)` 找不到模块 → **静默退回任务管理**。
  三个模块全中招，且不报错（所以看起来像"还在解耦阶段"）。
- **修法**（`desktop/modules/shell.py`）：`_module_click_handler(key)` /
  `_tasks_click_handler()` 返回 `lambda _checked=False: ...`，**显式吞掉那个 bool**。
  顺手存 `self._tasks_item`（回任务管理要用）。
- 回归钉子：`tests/selftests/modules_shell.py` 6a —— **真点导航条目**
  （`_module_items[key].click()`），断言 route 与当前页类型，而不是只测
  `show_module()`。这类"信号签名变了导致槽参数错位"的 bug，只有真点才抓得到。
- 真机验证（真实 `MainWindow` + 展开导航）：extract/rembg/imposition 依次切到
  对应页，回任务管理也正常。

### 2) 「提取 → 去底色」连不上（真 bug，实测断链）

- 现象：把 extract 的**输出根**拖给「去底色」→ 功能层只扫顶层 → 报
  "未在 …\样书_提取 找到任何图片文件"。
- 两个成因，都修了：
  1. **入口**：`StepSpec.resolve_source` / `collect_files` 顶层找不到文件时
     **自动下钻 1~2 层**（`AUTO_DESCEND_DEPTH = 2`，`nested_listing` 广度优先）。
     恰好一个子目录装着 → 自动指过去并交代一句；多个 → **拒绝**并让用户挑一个
     （混着处理会把不同书的页拼在一起）。
  2. **出口**：`functions.extract` 的布局是 `<输出>/<PDF名>/images/`
     （`utils.pdf_extract.run_on_input_directory`，与 CLI 同源）。单 PDF 时这层
     嵌套多余且**违背本层"输出目录精确生效"的承诺**，于是新增
     `StepSpec.flat_output`（只有 extract 为真）+ `kernel.job_for(spec)` 装上
     `_flatten_single_pdf_output` 收尾钩子：把 `<输出>/<PDF名>/**` 平铺到
     `<输出>/` 再删空壳；**同名冲突则整个不动**（宁可多留一层也不覆盖/丢产物）；
     源是**目录**（批量）时**保持**每个 PDF 一个子目录。
- ⚠️ **造 job 只走 `kernel.job_for(spec)`**：哪一步需要收尾只有它知道，
  在别处再拼一次 `command_job` 就一定会漏（`StepControl` 已改为 `job_for`）。
  `job_for` 内部按 `spec.command` 装配（不写死 `extract_job()`），将来别的步骤
  要平铺只改 `flat_output=True`。
- 实测（进程内内核，绕开本机 QProcess 起不来的问题）：
  extract 3 页 → 3 张 jpg **平铺在输出根**；把输出根拖给 rembg → 3 张 png。
  另用探针确认 rembg 的产物**就落在 dest 根下**（顶层 `1.png/2.png`，没有多余
  的 `rembg/` 那层）。

### ⚠️ 先说被推翻的：信号跨线程那条是**误报**

wait/processEvents 循环）三种写法全部在主线程执行**：PySide6 对无接收者的
普通函数会**自动建 proxy QObject 并给queued 连接**。

⇒ 别照agent 说的去"修"一个不存在的问题。但**仍改成显式
`connect_queued`**（项目约定 `desktop/workers/worker_host.py`）——依赖版本
相关的隐式行为是隐患，不是修复。留了注释说明实测结论与仍要显式化的理由。

### 真正修的 4 处（每条都先写了复现脚本）

1. **`_BakeWorker.run()` 吞异常 → 静默失败**（用户最可能遇到的"点了没反应"）
   - 实测：`QThread.run` 抛异常**不杀进程**（PySide6 6.9.2 只打 stderr），
     但 `result=None` + `cancelled=False` ⇒ 上层 `_commit_deform` 把它当成
     "**用户取消**"，弹掉撤销点，**一声不吭**。用户点 20 秒什么也没发生。
   - 修：`run()` 捕获 `Exception` + `BaseException` 存 `self.error`；
     `run_with_progress` 在线程停后 **`raise worker.error`**。
   - ⚠️ **返回前必须在 `finally` 之前读 `cancelled`/`result`**：收尾要调
     `worker.cancel()`，读了会污染。**我自己先踩了这个坑**（正常完成被判取消）。

2. **变换笼 RBF 奇异矩阵**（`utils/cage_warp.py`）
   - 实测：两个把手拖到重合 ⇒ Wendland `φ(0)=1` ⇒ 矩阵严格奇异 ⇒
     `LinAlgError`，从 Qt 槽逸出崩溃。
   - 修：新增 `_drop_coincident()` **相对判据**去重（`_COINCIDENT_REL=1e-3`）+
     半径迭代发散检测 + `except LinAlgError` 兜底退化为恒等。
   - **绝对容差 1e-6 不够**（实测踩到）：相距 0.5px 时是**近**奇异，
     `solve` 不抛而是权重炸到 1e14，把半径迭代带进发散。
   - **顺带挖出一个既有算法缺陷**（改前就会崩）：半径迭代
     `r ← 1.1·|φ'|max·Σ|w|` 在**位移互相抵消**时**发散**——实测两把手反向拖
     半径逐轮 212→1099→23027→9.6e6→1.7e12，条件数 1.2e1→**inf**。
     加了 `_RADIUS_DIVERGE=1e4` 截断。
   - ⚠️ 副作用是**改进不是误伤**：原代码对同向双把手返回 `r=1.3e9`
     的荒谬半径（影响框会膨胀到天际），现在正确判为发散。

3. **校正退化抛异常 + 污染撤销栈**（更隐蔽）
   - 实测 3 种退化输入（完全共线/两点重合/极细长）**全部抛 ValueError**
     而非返回 null 图，而 `_commit_rectify` 只判 `done.isNull()`。
   - 双重后果：异常逸出 + **`_push_undo` 已压栈但 `pop()` 被跳过** ⇒
     撤销历史永久错位（Ctrl+Z 撤销空操作）。改try/except 成对处理。

4. **编辑器缺 `closeEvent` + 「完成」重入**
   - 缺 closeEvent ⇒ 线程在飞时对话框析构 ⇒
     `QThread: Destroyed while thread is still running` ⇒ **abort**。
   - 「完成」整体无幂等：三个 busy 标志只挡**同名**方法，挡不住整体重入。
     烘焙的 `processEvents` 会派发排队的第二次点击（**快速双击即可**）⇒
     两个 worker + 两个对话框并行。已加 `_finishing` 幂等标志。
   - 另给 `cage_move`/`cage_move_all` 补了位置夹取（原先缺 `pin_move`/
     `quad_move` 都有的保护，把手能飘到几万像素外 ⇒ 画布膨胀几个数量级）。

### 写测试的教训（自我提醒）

三次断言写错、都是**把"实现细节"当契约**：
①以为重合必须返回 None，实际去重后 1×1 矩阵可解、返回合法形变；
②以为反向拖是"正常场景"，实际它本来就会崩（原码抛 LinAlgError），
   `git stash` 对比基线才确认是**改进**不是误伤；
③以为退化笼应"逐字节还原"，实际合并后仍有平均位移、是真形变。
⇒ 断言要写**可观测性质**（不抛、尺寸不变、不出黑图），别写实现细节。
